已完成DataStream API 与执行图

本章先记住 3 件事
  • 管道三段：任何作业都是 Source → Transformation → Sink；Transformation 是算子链，不是单独「阶段类」。
  • 并行度：并行度 决定每个算子有多少并行 Subtask；集群上受 TaskManager Slot 总数约束，不是越大越快。
  • 执行图：keyBy 会引入网络 shuffle；Client 把 API 链编译成 JobGraph，JobMaster 再展开为 ExecutionGraph 并部署到 TaskManager。

Source → Transformation → Sink

DataStream 程序本质是有向无环图（DAG）：Source 产生流，Transformation 逐条变换，Sink 消费结果。

flowchart LR
  S[Source\nSocket / Kafka / fromElements]
  T1[Transformation\nmap / filter / keyBy]
  T2[Transformation\nprocess / window]
  K[Sink\nprint / File / JDBC]
  S --> T1 --> T2 --> K

记忆口诀：一条 DAG，从 Source 流入，经若干算子，最后在 Sink 落地；编译后才会切成并行 Task（见第四节「执行图」）。

Source

产出 DataStream<T>，如 fromElements、Socket、Kafka；决定输入格式与事件时间属性（高级章节展开）。

Transformation

对流做计算：map、filter、flatMap、keyBy、window 等；返回仍是 DataStream 或 KeyedStream。

Sink

写出结果：print（学习用）、文件、消息队列等；与 Source 一起决定端到端语义（at-least-once / exactly-once）。

map、filter、flatMap 与并行度

算子输入:输出作用示例
map 1 : 1 逐条映射 .map(x -> x * 2)
filter 1 : 0 或 1 条件过滤 .filter(x -> x > 0)
flatMap 1 : N 一对多展开 拆行、拆词

并行度：每个算子可独立设置「并行实例数」—— 全局默认 → 算子覆盖 → 提交参数。

  • 单算子：.map(...).setParallelism(4)
  • 全局默认：env.setParallelism(2)
  • 提交时 CLI：flink run -p 4 ...

并行度不能超过可用 Slot 总数；Web UI 中 Task 数量与 Subtask 索引对应本章 Demo 的 print 行首输出。

示例代码：并行度与算子级设置

java 
// 并行度：全局、单算子、提交参数（三选一或组合）
env.setParallelism(2);
someStream.map(...).setParallelism(4);
// flink run -p 8 target/transform-lab.jar

// keyBy 后按账户分区（Walkthrough 风格，与第三节呼应）
transactions
    .keyBy(Transaction::getAccountId)
    .process(new FraudDetector())
    .name("fraud-detector")
    .setParallelism(4);

示例代码：本章 Demo 完整管道

下方代码对应 demos/basics-03-datastream-transform-lab 中的 TransformLabJob，串联 flatMap → map → filter → keyBy → print，后文执行图均以此为例。

java 
// TransformLabJob — 对应 demos/basics-03-datastream-transform-lab
StreamExecutionEnvironment env = StreamExecutionEnvironment.getExecutionEnvironment();
env.setParallelism(2);

DataStream<String> lines = env.fromElements(
    "alice 100", "bob 50", "alice 30", "charlie 200",
    "invalid-line", "bob 10");

DataStream<Tuple2<String, Integer>> pairs = lines
    .flatMap((String line, Collector<String[]> out) -> {
        String[] parts = line.split(" ");
        if (parts.length == 2) {
            out.collect(parts);
        }
    })
    .returns(String[].class)
    .map(parts -> Tuple2.of(parts[0], Integer.parseInt(parts[1])))
    .filter(t -> t.f1 >= 50);

pairs.keyBy(t -> t.f0)
     .map(t -> Tuple2.of(t.f0, t.f1))
     .print();

env.execute("transform-lab");

keyBy 与数据分区

keyBy 按 key 的 hash 将记录路由到下游 Subtask，保证相同 key 进入同一并行实例，从而能使用 Keyed State、窗口按 key 聚合等。

flowchart TB
  subgraph before["keyBy 前 parallelism=3"]
    P0[Subtask 0]
    P1[Subtask 1]
    P2[Subtask 2]
  end
  KB[keyBy userId]
  subgraph after["keyBy 后 — hash 分区"]
    K0[userId hash → 0]
    K1[userId hash → 1]
    K2[userId hash → 2]
  end
  P0 --> KB
  P1 --> KB
  P2 --> KB
  KB --> K0
  KB --> K1
  KB --> K2

注意：keyBy 之后得到 KeyedStream，再 process / 窗口 / 状态都按 key 隔离；不要在 KeyedStream 上再次 keyBy。

  • KeySelector：.keyBy(event -> event.getUserId()) 或方法引用 Event::getUserId。
  • 数据倾斜：个别 key 过多会导致某 Subtask 成为热点（practice / advanced 讲 rebalance 与自定义分区）。
  • 与 rebalance 区别：keyBy 是 hash 分区；rebalance / rescale 是轮询或局部轮询，不保证相同 key 同 Subtask。

从逻辑图到物理执行计划

以 Demo TransformLabJob 为例：fromElements → flatMap → map → filter → keyBy → print。下面用同一管道从调用链、逻辑图到物理部署逐层展开。

层次图 / 产物谁生成关注点
代码层Java API 链开发者可读的业务 DAG
execute() 前StreamGraphFlink Client与 API 一一对应的 StreamNode
优化后JobGraphClient算子链合并、keyBy 处 Shuffle

动手练习

按顺序完成下列步骤；图中标签（A1、B1、C1 等）仅用于与上文插图对照，不会出现在右侧大纲里。

  1. 阅读前三节，对照「示例代码：本章 Demo 完整管道」画出你自己的 Source → Transformation → Sink 草图。
  2. 运行 Demo：cd demos/basics-03-datastream-transform-lab && mvn -q exec:java，在 IDE 于 execute 前后设断点，对照图 A1 理解 Client 与 Cluster 分工。
  3. 对照图 B1→B3：数清 StreamGraph 节点数、JobGraph 的 Vertex 数；可选 mvn -q exec:java -Dexec.args=4，在 Web UI 核对 Subtask 数量。
  4. 在 Web UI Task Graph 找图 B2 的 Vertex 与 keyBy 后的 Shuffle 边；观察 print 输出，同用户名（key）是否落在相同 subtask 索引（图 C1）。
  5. （可选）mvn package 后 flink run 提交 Standalone，在 Jobs 列表对照图 A1 的作业状态变化。
