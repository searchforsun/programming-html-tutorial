已完成Flink 定位与流批一体架构

本章先记住 3 件事
  • 解决什么：对无界数据流做低延迟、有状态的实时计算，并保证故障后可恢复。
  • 谁协作：流处理 运行时由 JobManager 协调、TaskManager 执行，Client 负责提交作业。
  • 怎么写：DataStream 最灵活；多数分析场景优先 Table API / Flink SQL。

流处理 vs 批处理：为何需要 Flink？

传统批处理（如离线 Hive/Spark Batch）按有界数据集切分、周期性跑作业；而业务事件（点击、支付、传感器）是持续到达的，需要「来一条算一条」或「按窗口聚合」。

  • 低延迟 — 秒级甚至毫秒级产出结果，而不是等 T+1 报表。
  • 有状态 — 需要记住用户会话、累计金额、去重键等，单靠无状态 map/filter 不够。
  • 精确一次 — 故障重启后，输出与副作用尽量不重复；依赖 Checkpoint 与 Source/Sink 协同（进阶章展开）。

核心组件：JobManager、TaskManager、Slot

Client

解析程序、生成 JobGraph，提交给 JobManager；可在 IDE 本地跑，也可 detached 提交到集群。

JobManager

调度资源、协调 Checkpoint；内含 Dispatcher（REST/Web UI）、JobMaster（单作业执行）、ResourceManager（Slot 分配）。

TaskManager

Worker 进程，执行算子 Task，在 Slot 间交换数据流；一个集群通常有多个 TaskManager。

Slot

TaskManager 内的资源切片，是调度最小单位；Slot 数 ≈ 集群并行能力上限。

DataStream / Table / SQL 三层 API 如何选型

API 层抽象典型场景何时优先
DataStream 事件流上的算子（map、keyBy、ProcessFunction） 复杂状态机、自定义窗口、细粒度时间控制 需要完全掌控状态、时间语义与底层逻辑时
Table API 关系型动态表 + 连续查询 ETL、实时数仓、指标聚合 业务以「表」思维建模，希望优化器自动选算子
Flink SQL 声明式 SQL（流批统一） 实时报表、即席分析、与 BI 工具对接 团队熟悉 SQL、希望降低 Java 样板代码时

官方建议：多数数据分析从 Table/SQL 起步；DataStream 与 Table 可互操作。

版本线：2.x Stable 与 1.20 LTS 怎么选

  • Flink 2.2 Stable — 本教程与文档以此为主。
  • Flink 1.20 LTS — 不少生产集群仍运行 1.x；API 思想一致，注意连接器版本矩阵。
  • 选型建议 — 学习/新项目跟 Stable；对接现有 1.20 集群以集群文档为准。
