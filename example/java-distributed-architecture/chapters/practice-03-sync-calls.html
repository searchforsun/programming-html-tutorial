为什么要学本章

上一章 有了注册发现与网关入口，但 order-service 还不知道怎么调用 inventory-service。本章引入 OpenFeign 声明式 HTTP 客户端，配合 服务发现 与 Spring Cloud LoadBalancer，把 URL 从硬编码变成声明式接口，并补齐超时、重试与错误处理——让 ShopFlow 下单链路真正跑通。

本章先记住 3 件事
  • Feign 是接口，不是实现：只需声明 DTO 映射与路径，框架自动生成代理；切勿在 Controller 里手写 new RestTemplate().postForEntity(...)。
  • 超时 + 重试 ≠ 可靠：下游必须 幂等，否则多次调用会多扣库存（分布式数据：事务、幂等与 Saga 展开）。
  • LoadBalancer 只选实例，不保证可用：选到的实例仍可能宕机，需配合熔断（韧性工程）。

声明式 HTTP 客户端与 DTO 映射

ShopFlow · order → inventory 第一步 用户下单时，order-service 需同步调用 inventory-service 预留库存。团队不想写 RestTemplate 的 host/port/header 样板——能否像调本地方法一样调远程服务？

OpenFeign 是 Spring Cloud 的声明式 HTTP 客户端：定义 Java 接口 → 加 @FeignClient 注解 → 方法签名字段映射为请求路径、参数与返回体。Feign 在运行时生成代理，自动完成 JSON 序列化/反序列化。相较于手写 RestTemplate，Feign 把「怎么调」托管给框架，团队只关注「调什么」。

RestTemplate 样板
  • 每次调用手写 URI 拼接、header 设置
  • 泛型 ParameterizedTypeReference 易出错
  • 超时、重试需另配 RequestConfig
Feign 声明式
  • 接口 + 注解即客户端；DTO 复用 api 模块
  • 返回类型直接写 ReserveResponse
  • 超时/重试集中在配置文件

Inventory Feign 接口（定义在 order-api）

java 
// shopflow-order-api / com.shopflow.order.client.InventoryClient
@FeignClient(name = "inventory-service", path = "/api/reservations")
public interface InventoryClient {

  @PostMapping
  ReserveResponse reserve(@RequestBody ReserveRequest request);

  @GetMapping("/{reservationId}")
  ReserveStatus status(@PathVariable String reservationId);
}

name = "inventory-service" 即 spring.application.name，与 Eureka 注册名一致。无需写 url——配合 LoadBalancer 解析。

DTO 放在订单 api 模块（契约复用）

java 
// shopflow-order-api / com.shopflow.order.dto
public record ReserveRequest(
  @NotBlank String sku,
  @Positive  int quantity,
  @NotBlank String idempotencyKey  // 幂等键：重复提交返回同一结果
) {}

public record ReserveResponse(
  String reservationId,
  ReserveStatus status,
  int reservedQty
) {}
先想 10 秒：为何 DTO 放在 order-api 而非 inventory 侧？

消费者定义期望的契约字段（领域建模、边界上下文与 API 契约 中 消费者驱动契约）。inventory 实现时可参考同名字段，跨上下文不共享实体——防止模型泄漏。

Spring Cloud LoadBalancer 与实例选择

@FeignClient 与 spring-cloud-starter-loadbalancer 配合后，name 会自动解析为 lb://inventory-service：先从 Eureka 拉取实例列表，再按策略选一个。Spring Cloud 2025 默认使用 RoundRobinLoadBalancer，也可切换为随机或基于 Zone 的偏好。

LoadBalancer 配置（可选切换策略）

yaml 
# order-service / application-local.yml
spring:
  cloud:
    openfeign:
      client:
        config:
          inventory-service:
            connectTimeout: 2000
            readTimeout: 5000
    loadbalancer:
      configurations: round-robin  # 默认；也可 random

Feign 代理拦截调用 → LoadBalancer 查注册表 → 选实例 → 发起 HTTP。实例列表由 Eureka 定期刷新，并非每次调用都查注册中心。

  • 依次轮转实例；默认策略
  • 适合各节点规格一致
  • 无状态服务首选
  • Random：随机选，适合压测分散
  • ZonePreference：同可用区优先，降低跨 AZ 延迟
  • Spring Cloud 2025 通过 ServiceInstanceListSupplier 扩展

超时、重试与错误解码策略

同步调用中最容易踩的坑：默认超时过长导致线程池耗尽，或重试不幂等导致重复扣减。ShopFlow 约定：connectTimeout 2s + readTimeout 5s，重试仅针对 可重试状态码（503/网络异常），且请求必须带 幂等键。

Feign 超时与重试配置（Spring Cloud 2025）

yaml 
# order-service / application-local.yml
spring:
  cloud:
    openfeign:
      client:
        config:
          inventory-service:
            connectTimeout: 2000
            readTimeout: 5000
            retryer: com.shopflow.common.ShopFlowRetryer
      compression:
        request:
          enabled: true
        response:
          enabled: true

自定义 Retryer：指数退避 + 仅可重试异常

java 
// shopflow-common / com.shopflow.common.ShopFlowRetryer
public class ShopFlowRetryer implements Retryer {
  private final int maxAttempts = 3;
  private final long backoffMs = 300;
  private int attempt = 1;

  @Override
  public void continueOrPropagate(RetryableException e) {
    if (attempt++ > maxAttempts) throw e;
    // 仅 5xx 或网络异常重试；4xx 直接抛出
    if (e.status() >= 400 && e.status() < 500) throw e;
    try {
      Thread.sleep(backoffMs * (1L << (attempt - 2))); // 300 → 600
    } catch (InterruptedException ignored) {
      Thread.currentThread().interrupt();
    }
  }

  @Override
  public Retryer clone() { return new ShopFlowRetryer(); }
}

ErrorDecoder：区分 4xx / 5xx

java 
// shopflow-order-service 配置类
@Bean
public ErrorDecoder inventoryErrorDecoder() {
  return (methodKey, response) -> {
    if (response.status() == 409) { // 库存不足
      return new InsufficientStockException("库存不足，请稍后");
    }
    return new FeignException.FeignServerException(
      response.status(), "inventory 调用失败", response.request(), null, null);
  };
}
重试风暴
  • 无退避：3 次均在 0ms 后立即重试
  • 4xx 也重试（400 Bad Request 重试仍 400）
  • 被调用方无幂等键 → 重复扣库存
安全重试
  • 300ms → 600ms 指数退避，给下游恢复时间
  • 仅 5xx / IOException 重试
  • 每个请求附 Idempotency-Key 头

ShopFlow：下单链路同步调用 inventory

order-service 收到 POST /orders 后：校验参数 → 生成 orderId → 同步调用 inventory reserve → 若预留成功则持久化订单、返回 201；若库存不足（409）则返回友好错误。本章暂不涉及 payment——那是 Kafka 事件驱动与 Redis 缓存 的事件通知环节。

OrderService：编排 reserve + 持久化

java 
// order-service / com.shopflow.order.service.OrderService
@Service
public class OrderService {
  private final InventoryClient inventoryClient;
  private final OrderRepository orderRepo;

  public CreateOrderResponse createOrder(CreateOrderRequest req) {
    // 1. 幂等键：requestId 或客户端生成
    String idempotencyKey = req.idempotencyKey();

    // 2. 同步预留库存
    ReserveResponse reserve = inventoryClient.reserve(
      new ReserveRequest(req.sku(), req.quantity(), idempotencyKey));

    if (reserve.status() == ReserveStatus.INSUFFICIENT) {
      throw new InsufficientStockException("SKU " + req.sku() + " 库存不足");
    }

    // 3. 持久化订单（本地 ACID）
    Order order = Order.create(req, reserve.reservationId());
    orderRepo.save(order);

    return CreateOrderResponse.from(order, reserve);
  }
}

Controller：REST 入口

java 
@RestController
@RequestMapping("/orders")
public class OrderController {
  private final OrderService service;

  @PostMapping
  public ResponseEntity<CreateOrderResponse> create(
      @Valid @RequestBody CreateOrderRequest req) {
    return ResponseEntity.status(201).body(service.createOrder(req));
  }
}

  C->>G: POST /api/orders

  O->>I: Feign POST /api/reservations
  I->>I: 扣减库存（串行化）

  O->>O: 持久化订单
  O-->>G: 201 {orderId, status: CREATED}
  G-->>C: 201

若 inventory 返回 409（库存不足）或超时（readTimeout 5s），order 不落库，返回对应错误码。幂等键保证重复提交不会多扣。

先想 10 秒：为何不先落库订单再调 inventory？

若先落库后 reserve 失败，需回滚或补偿已落库的订单——即 Saga。保持「先 reserve → 再落库」的顺序，失败时订单未落库、无需补偿。但 inventory 若成功而订单落库失败，仍需补偿（分布式数据 展开）。

契约测试与 Mock 服务协作

order-service 单元测试中不应启动真实 inventory；用 WireMock 或 Spring Cloud Contract 模拟下游行为，在 CI 中每次 PR 都验证 order 对 inventory 契约的兼容性。这与 领域建模、边界上下文与 API 契约 的 消费者驱动契约 一致：order 先写期望，inventory 侧验证能否满足。

WireMock 桩：模拟 inventory reserve 成功

java 
// order-service / src/test
@SpringBootTest
@WireMockTest(httpPort = 8082)
class OrderServiceIntegrationTest {

  @DynamicPropertySource
  static void overrideInventoryUrl(DynamicPropertyRegistry reg) {
    // 让 Feign 指向 WireMock 而非真实 inventory
    reg.add("spring.cloud.openfeign.client.config.inventory-service.url",
            () -> "http://localhost:8082");
  }

  @Test
  void shouldCreateOrderWhenInventoryReserveSucceeds() {
    stubFor(post(urlEqualTo("/api/reservations"))
      .willReturn(aResponse()
        .withStatus(201)
        .withHeader("Content-Type", "application/json")
        .withBody("""
          {"reservationId":"r-1","status":"RESERVED","reservedQty":1}""")));

    // 调用 orderController 或 service
    var resp = restTemplate.postForEntity("/orders", req, CreateOrderResponse.class);
    assertThat(resp.getStatusCodeValue()).isEqualTo(201);
    assertThat(resp.getBody().status()).isEqualTo("CREATED");
  }

  @Test
  void shouldReturn409WhenInventoryInsufficient() {
    stubFor(post(urlEqualTo("/api/reservations"))
      .willReturn(aResponse()
        .withStatus(409)
        .withBody("""{"error":"INSUFFICIENT","message":"库存不足"}""")));

    assertThatThrownBy(() -> service.createOrder(req))
      .isInstanceOf(InsufficientStockException.class);
  }
}

Mock 让 order 侧在无真实 inventory 时仍能验证：① 正常预留后落库 ② 库存不足时的异常分支 ③ 超时/5xx 时的重试行为。inventory 侧再跑 Pact/Spring Cloud Contract 验证其实现能通过 order 的契约。

Feign 常见问题速查
现象根因修复
UnknownHostException on inventory-service未加 loadbalancer 依赖或 Eureka 未就绪确认 spring-cloud-starter-loadbalancer；先起 Eureka
Feign 返回 200 但 body 为 nullDTO 字段名与 JSON 不匹配检查 @JsonProperty 或 record 命名
重试 3 次后仍 503实例全部宕机或健康检查未通过检查 Eureka 控制台实例状态；考虑 circuit breaker

本章结论

每条对应上一节 h3，practice 阶段实操递进。

  • Feign 声明式调用：@FeignClient(name="inventory-service") + DTO 契约；无需手写 RestTemplate 样板，跨上下文只依赖 api 模块。
  • LoadBalancer 选实例：lb:// 前缀触发 RoundRobin；实例列表由 Eureka 定期刷新而非每次调用都查。
  • 安全重试：指数退避 300→600ms，仅 5xx/IO 重试，4xx 直接失败；每个请求必须带幂等键。
  • 下单链路：先 reserve → 再落库，失败时不产生需补偿的孤儿订单；但 inventory 成功 + order 落库失败仍需补偿。
  • 契约测试：WireMock 模拟下游，order 独立验证正常/异常/超时分支；CI 中跑消费者契约，集成失败左移到 PR。

动手练习

为 order-service 接入 Feign 调用 inventory，配置超时重试策略，并用 WireMock 编写两个分支测试。

操作步骤

  1. 在 order-api 定义 InventoryClient 接口与 ReserveRequest/Response DTO，对照「Inventory Feign 接口」代码块。
  2. order-service 添 Feign/LoadBalancer 依赖，启动 Eureka + inventory + order（参考 上一章 顺序），观察 lb://inventory-service 解析日志。
  3. 按「Feign 超时与重试配置」yaml，将 connectTimeout 设为 100ms 制造超时，验证指数退避重试后仍失败时抛出 RetryableException。
  4. 运行 WireMock 测试：正常 reserve 返回 201 与库存不足 409 两个分支，确保不依赖真实 inventory。

判断练习

  1. Feign 调用 inventory 返回 404，日志显示 POST /api/reservations 返回 404。请排序排查步骤：A) 检查 inventory Controller 映射路径；B) 确认 Eureka 上 inventory-service 为 UP；C) 检查 order 侧的 Feign path 属性；D) curl inventory 直连端口。

    参考答案

    正确顺序：B → C → D → A。Eureka 注册正常才能排除服务发现问题；然后核对 Feign 的 path 参数与 Controller 的 RequestMapping 是否一致；直连 curl 验证下游可达；最后确认 Controller 代码路径。

  2. 以下重试配置：maxAttempts=5, backoffMs=50，且 4xx 也重试、inventory 无幂等键。找出 3 处违反本章推荐的地方，并各用一句话说明修正。

    参考答案

    ① maxAttempts=5 过多 → 建议 3（减少无效重试时延）。② backoffMs=50 无指数退避 → 改为 300ms 起步 ×2 翻倍，给下游恢复时间。③ 4xx 也重试且无幂等键 → 仅 5xx/IO 重试；下游加幂等键防重复扣减。
