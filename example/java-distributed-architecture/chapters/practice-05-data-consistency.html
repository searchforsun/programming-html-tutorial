分布式数据：事务、幂等与 Saga

约 45 分钟 · 阶段：Java 微服务栈实战 · 能力：用 Seata AT + Saga 补偿 + Outbox 模式处理跨服务数据一致性，practice 阶段收官

为什么要学本章

同步调用 中出现的「inventory 成功但 order 落库失败」、Kafka 事件 中「消息发了但 DB 没写」——都是分布式数据一致性的经典坑。本章用 Seata AT 实现自动回滚、Saga 编排补偿事务、Outbox 保证「写库 + 发消息」原子性，并补齐幂等表与业务唯一键的实际代码。practice 阶段三章形成一个完整闭环：调得通 → 扛得住 → 错得对。

  • 选择 Seata AT、Saga 或 TCC 中的合适方案并写出配置与补偿代码
  • 用 Outbox 模式原子化「写业务表 + 发 Kafka 消息」

本章先记住 3 件事
  • 分布式事务没有免费午餐：每种方案都在一致性、可用性与复杂度之间取舍；不要把 AT 当万能药。
  • 幂等是分布式系统第一戒律：网络不可靠 → 必然重试 → 必须幂等。幂等表或业务唯一键，每条写路径至少选一个。
  • Outbox 先写后发：事件与业务数据同一本地事务写入 outbox 表，异步 relay 投递到 Kafka——这是保证「DB 有记录 ⇔ Kafka 有消息」的唯一安全路径。

本地事务边界与跨库问题

ShopFlow · 二选一的死局 Feign 调用链路 中 order 先 reserve 再落库：若 inventory 返回 201 但 order 落库时 DB 宕机——库存已扣、订单没记录。单服务内可以用 @Transactional 回滚，跨两个独立数据库就再也回不去了。

本地事务（ACID）在单数据库内可用 ACID 保证原子性：@Transactional 包裹下单 → 订单+明细同一连接、同一提交。但 ShopFlow 的 order DB 与 inventory DB 是两个独立 PostgreSQL 实例——@Transactional 无法跨连接。

跨库场景：原子性边界断裂
sequenceDiagram
  participant O as order-service
  participant ODB as Order DB
  participant I as inventory-service
  participant IDB as Inventory DB

  O->>I: POST /reserve
  I->>IDB: UPDATE stock SET qty = qty - 1
  IDB-->>I: OK (committed)
  I-->>O: 201 {reservationId}
  O->>ODB: INSERT INTO orders...
  ODB--xO: Connection timeout!
  Note over O,ODB: 库存已扣、订单丢失

两个数据库独立提交，中间任何失败都会导致不一致。分布式事务要解决的就是这种多参与者场景。

场景适用方案ShopFlow 示例
单服务多表 @Transactional ACID 订单+明细同一 DB
跨 2～3 服务、实时一致性 Seata AT order + inventory 同步预留
跨多服务、长流程 Saga 编排 + 补偿 下单→支付→物流（小时级）
异步事件 + DB 原子性 Transactional Outbox 发 OrderCreated 与订单同事务

Seata AT 模式与适用边界

Seata AT（Automatic Transaction） 是阿里开源的分布式事务方案，对业务代码侵入最低：只需在全局事务发起方加 @GlobalTransactional，Seata 自动管理 undo_log 并做两阶段提交。但 AT 要求各参与方使用支持 ACID 的关系型数据库（MySQL/PostgreSQL），且不适合长事务。

全局事务发起方：order-service

java 
// order-service / OrderService
@GlobalTransactional  // 替代 @Transactional，标记全局事务
public CreateOrderResponse createOrder(CreateOrderRequest req) {
  // 1. RPC 调 inventory reserve（参与方自动加入全局事务）
  ReserveResponse reserve = inventoryClient.reserve(
    new ReserveRequest(req.sku(), req.quantity(), req.idempotencyKey()));

  if (reserve.status() == ReserveStatus.INSUFFICIENT) {
    throw new InsufficientStockException("库存不足");
  }

  // 2. 本地持久化（Branch Transaction）
  Order order = Order.create(req, reserve.reservationId());
  orderRepo.save(order);

  return CreateOrderResponse.from(order, reserve);
  // 3. 任何一步抛异常 → Seata 协调二阶段回滚
}
AT 不适合的场景
  • 长事务（锁定资源数秒以上，并发急剧下降）
  • 非关系型数据库参与方（MongoDB、Redis）
  • 外部不可回滚操作（发邮件、调用第三方支付）
AT 适合的场景
  • 2～3 个关系型数据库的短事务
  • 不希望改造业务代码（加一张 undo_log 表即可）
  • 需要强一致、可接受短暂锁等待
先想 10 秒：AT 模式下 inventory reserve 成功后若 Seata Server 宕机，会发生什么？

一阶段已提交的本地事务不会自动回滚；需 Seata Server 恢复后读取 undo_log 做二阶段回滚。这期间数据处于「已提交但不一定生效」的中间态——AT 并非真正的同步强一致，依赖 Seata Server 可用性。

Saga 编排：补偿事务设计

当流程超过 2 个参与者或涉及不可自动回滚的操作（如调用第三方支付），Saga 比 AT 更合适。Saga 把长事务拆成有序的本地事务序列，每个正向步骤对应一个补偿步骤：正向成功 → 继续下一步；正向失败 → 反向执行已成功步骤的补偿。

ShopFlow 下单 Saga（编排式）

Saga 正向与补偿序列
flowchart TD
  S1["① reserveInventory
预留库存"] -->|成功| S2["② createOrder
创建订单"]
  S1 -->|失败| E1[结束：库存不足]
  S2 -->|成功| S3["③ initiatePayment
发起支付"]
  S2 -->|失败| C1["⏪ releaseInventory
释放库存"]
  S3 -->|成功| DONE[✅ 下单完成]
  S3 -->|失败| C2["⏪ cancelOrder
取消订单"]
  C2 --> C1

编排式 Saga：order-service 作为协调者依次调用各步骤；任一步骤失败则逆序执行补偿。注意：补偿也可能失败，需重试或人工介入。

Saga 协调者（order-service）

java 
// order-service / SagaOrchestrator
@Component
public class CreateOrderSaga {
  private final InventoryClient inventoryClient;
  private final PaymentClient paymentClient;
  private final OrderRepository orderRepo;

  public CreateOrderResponse execute(CreateOrderRequest req) {
    String reservationId = null;
    String orderId = null;

    try {
      // Step 1: reserve
      reservationId = inventoryClient.reserve(req.sku(), req.quantity(), req.idempotencyKey());
    } catch (Exception e) {
      throw new SagaFailedException("reserve failed", e); // 无需补偿
    }

    try {
      // Step 2: create order
      Order order = Order.create(req, reservationId);
      orderRepo.save(order);
      orderId = order.getId();
    } catch (Exception e) {
      // 补偿 Step 1
      inventoryClient.releaseReservation(reservationId);
      throw new SagaFailedException("createOrder failed, compensated", e);
    }

    try {
      // Step 3: initiate payment
      paymentClient.initiate(orderId, req.amount());
    } catch (Exception e) {
      // 补偿 Step 2 → Step 1
      orderRepo.markCancelled(orderId);
      inventoryClient.releaseReservation(reservationId);
      throw new SagaFailedException("payment failed, compensated", e);
    }

    return new CreateOrderResponse(orderId, "CREATED");
  }
}
  • 中心协调者控制步骤顺序与补偿
  • 流程清晰、易于监控与排障
  • 协调者成为单点，需持久化状态
  • ShopFlow 选择：order-service 为协调者
  • 各服务订阅事件自行决定下一步
  • 无中心协调者，扩展性好
  • 流程分散、排障需跨服务追踪
  • 配合 Kafka 可实现（见 事件驱动）

幂等表、业务唯一键与重复提交

无论 AT 还是 Saga，网络抖动都可能让同一请求被多次执行。幂等 不是「不重复」——是「重复执行与执行一次结果相同」。ShopFlow 两种实现方式视场景选用：

方式一：幂等表（通用、精确）

java 
// order-service / IdempotencyService
@Transactional
public <T> T executeIdempotently(String idempotencyKey,
    Supplier<T> action, Function<String, Optional<T>> resultLookup) {

  // 1. 幂等表已有记录？返回原始结果
  Optional<T> existing = resultLookup.apply(idempotencyKey);
  if (existing.isPresent()) return existing.get();

  // 2. 插入幂等记录（唯一索引防并发 INSERT）
  try {
    idempotencyRepo.save(new IdempotencyRecord(idempotencyKey, "PROCESSING"));
  } catch (DataIntegrityViolationException e) {
    // 并发冲突：另一个请求已插入，等待并返回其结果
    return pollForResult(idempotencyKey, resultLookup);
  }

  // 3. 执行业务
  try {
    T result = action.get();
    idempotencyRepo.updateStatus(idempotencyKey, "DONE", toJson(result));
    return result;
  } catch (Exception e) {
    idempotencyRepo.updateStatus(idempotencyKey, "FAILED", null);
    throw e;
  }
}

方式二：业务唯一键（轻量、领域化）

sql 
-- order 表：order_request_id 为业务唯一键
ALTER TABLE orders ADD CONSTRAINT uk_order_request_id
  UNIQUE (order_request_id);

-- 重复 INSERT 直接失败，应用层 catch 后返回已有订单
INSERT INTO orders (id, order_request_id, user_id, sku, quantity, status)
VALUES (?, ?, ?, ?, ?, 'CREATED');
场景推荐方式理由
外部 API 入口（客户端重试）幂等表可返回原始结果，而非报错
Kafka 消费者重复消息幂等表（eventId 唯一）eventId 去重，消费一次
订单创建（业务唯一约束）业务唯一键requestId 天然唯一，无需额外表
幂等设计反模式速查
反模式风险修正
仅靠 UUID 请求头不加唯一约束并发 INSERT 产生重复记录幂等表用 unique index (key)
幂等检查与业务写在两个事务间隙中其他请求插入幂等记录与业务在同一事务
只幂等不返回原始结果客户端收到不同响应体存储并返回首次执行结果

Outbox 实现要点（与前章衔接）

java 
// order-service：Outbox 保证发消息与写库原子性
@Transactional
public void createOrderWithOutbox(CreateOrderRequest req) {
  // 1. 业务写入
  Order order = Order.create(req);
  orderRepo.save(order);

  // 2. Outbox 记录（同一事务）
  OutboxEvent event = new OutboxEvent(
    "OrderCreated",
    order.getId(),                // aggregateId
    toJson(OrderCreated.from(order)) // payload
  );
  outboxRepo.save(event);

  // 3. 事务提交后，relay 线程轮询 outbox 表 → 发 Kafka → 标记已发送
}

本章结论

每条对应上一节 h3。

  • 本地 vs 分布式事务：单库内 @Transactional 可用 ACID；跨 order/inventory/payment 三库时 ACID 边界断裂，需 AT/Saga/Outbox。
  • Seata AT：@GlobalTransactional + undo_log 自动二阶段；适合 2～3 关系型 DB 短事务，不适合长事务或非关系型参与方。
  • Saga 补偿：正向步骤 + 补偿步骤成对设计；编排式 order-service 做协调者，失败时逆序补偿；补偿也可能失败需重试/人工。
  • 幂等双方案：幂等表（通用，可返回原始结果）+ 业务唯一键（轻量，领域约束）；幂等检查必须在同一事务中。
  • Outbox + 验收：事件与业务同事务写入 outbox 表，异步 relay 投递 Kafka；10 项验收清单覆盖 practice 全阶段技能。

动手练习

为 ShopFlow 加入 Seata AT / Saga 一致性方案、幂等表与 Outbox，跑通补偿流程并逐项验收。

操作步骤

  1. 启动 Seata Server（Docker），按「依赖与配置」片段为 order / inventory 添加 Seata 依赖，验证 @GlobalTransactional 生效。
  2. 按「Saga 协调者」代码实现 order → reserve → create → compensate，模拟 inventory 成功 + order DB 失败，验证库存被释放。
  3. 在 order DB 创建幂等表（DDL），用 JMeter 同一 idempotencyKey 并发 10 次 POST /orders，确认仅创建 1 条订单。
  4. 实现 Outbox：同一事务写入 orders + outbox_events，用 @Scheduled 轮询 relay 到 Kafka，停 Kafka 后验证消息不丢。

判断练习

  1. Saga 补偿步骤 releaseInventory 执行时因网络故障也失败。排障顺序：A) 检查 inventory 服务是否存活；B) 人工介入或定时补偿 Job 重试；C) 查看 order-service Saga 状态表当前步骤。请排序。

    参考答案

    正确顺序：C → A → B。先查 Saga 状态表确认补偿卡在哪一步、是否已重试；再确认目标服务可用；最后人工介入或死信队列重试。Saga 的补偿失败无法自动保证必定成功——这是 Saga 的「最终一致」语义。

  2. 幂等表方案中：① UUID 请求头 ② 幂等记录无唯一索引 ③ 检查幂等在新事务、业务在另一事务。找出 3 处违反本章推荐的地方并各用一句话修正。

    参考答案

    ① 仅 UUID 请求头不够 → 加幂等表 unique index (idempotency_key)。② 无唯一索引 → 建 UNIQUE(idempotency_key) 并发防重复 INSERT。③ 幂等检查与业务分两个事务 → 合并到同一 @Transactional，利用唯一约束 + 异常重试保证原子性。
