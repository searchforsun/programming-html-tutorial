Kafka 事件驱动与 Redis 缓存

约 42 分钟 · 阶段：Java 微服务栈实战 · 能力：用 Kafka 发布订阅领域事件、Redis 缓存热点商品详情并防护三大缓存问题

为什么要学本章

上一章 完成了 order → inventory 同步调用，但下单后还需要异步通知 payment 扣款、给 analytics 记流水——同步链太脆。本章引入 Kafka 事件驱动 解耦支付、分析等后续流程；同时用 Redis 缓存 加速商品详情读取，并防范穿透、击穿与雪崩三类经典缓存问题。两者结合，ShopFlow 从「能调通」走向「能扛量」。

学完你能
  • 定义 OrderCreated、PaymentCompleted 等领域事件并发布/消费
  • 用 Spring Cloud Stream + Kafka Binder 配置生产者与消费者
  • 说明分区键选取如何影响消息有序性与消费并行度
  • 识别缓存穿透/击穿/雪崩并写出对应防护代码
  • 实现 Cache-Aside 读商品详情，缓存预热与逻辑过期
本章先记住 3 件事
  • 事件 = 已发生的事实：OrderCreated 是「订单已创建」的不可变记录，不是「请处理一下」的命令；消费者自行决定如何处理。
  • 缓存不是银弹：只加速读、不改变写路径正确性；缓存与 DB 的短时不一致必须接受并设计补偿（逻辑过期/双删）。
  • 有序性有代价：同一分区内有序，但跨分区无序；按 orderId 分区保证同一订单事件顺序，但并发度受分区数限制。

领域事件：OrderCreated、PaymentCompleted

ShopFlow · 下单后链 订单创建后，payment-service 要发起扣款、analytics 要记流水、notification 要发邮件——全都耦合在 order-service 的同步调用中。领域事件 把后续动作解耦：order 只发布事件，谁关心谁订阅。

领域事件（Domain Event） 是限界上下文内已发生的事实，用过去式命名、不可变、携带必要标识与时间戳。ShopFlow 核心事件：

事件发布者典型消费者携带字段
OrderCreated order-service payment、analytics、notification orderId、userId、sku、quantity、occurredAt
PaymentCompleted payment-service order（更新状态）、analytics paymentId、orderId、amount、paidAt
InventoryReserved inventory-service order（确认预留） reservationId、sku、quantity、reservedAt
同步链耦合
  • order → payment → analytics 串行阻塞
  • 下游宕机则整条链失败
  • 加新消费者要改 order 代码
事件驱动
  • order 只发事件，不关心谁消费
  • 下游宕机不影响 order 主流程
  • 加新消费者只需订阅 topic

OrderCreated 事件定义

java 
// shopflow-common / com.shopflow.event.OrderCreated
public record OrderCreated(
  String eventId,       // UUID，幂等去重用
  String orderId,
  String userId,
  String sku,
  int quantity,
  Instant occurredAt
) {
  public static OrderCreated from(Order order) {
    return new OrderCreated(
      UUID.randomUUID().toString(),
      order.getId(), order.getUserId(),
      order.getSku(), order.getQuantity(),
      Instant.now()
    );
  }
}
先想 10 秒：事件里该放完整订单明细还是仅 orderId？

放 关键标识 + 必要字段（userId、sku、quantity），让多数消费者无需回查即可工作。但大字段（如商品描述列表）应让消费者按 orderId 回查，避免事件体膨胀。这就是「胖事件 vs 瘦事件」的权衡。

Spring Cloud Stream / Kafka Binder 基础

Spring Cloud Stream 在消息中间件上提供统一编程模型。ShopFlow 选 Apache Kafka 作为 编舞 的事件总线，通过 spring-cloud-stream-binder-kafka 桥接：生产者用 StreamBridge 发消息，消费者用 java.util.function.Consumer 收消息——无需直接操作 Kafka Client API。

依赖与配置

xml 
<!-- order-service pom -->
<dependency>
  <groupId>org.springframework.cloud</groupId>
  <artifactId>spring-cloud-stream-binder-kafka</artifactId>
</dependency>
yaml 
# order-service / application-local.yml
spring:
  cloud:
    stream:
      kafka:
        binder:
          brokers: localhost:9092
      bindings:
        orderCreated-out-0:
          destination: shopflow.order.created
          producer:
            use-native-encoding: true
      function:
        definition: orderCreatedSupplier
    function:
      definition: paymentCompletedConsumer

生产者：StreamBridge 发事件

java 
// order-service / OrderService
@Component
public class OrderEventPublisher {
  private final StreamBridge streamBridge;

  public void publishOrderCreated(Order order) {
    OrderCreated event = OrderCreated.from(order);
    boolean sent = streamBridge.send("orderCreated-out-0", event);
    if (!sent) {
      log.warn("Kafka 发送失败，走补偿：orderId={}", order.getId());
      // 写入 outbox 表或死信队列（practice-05 展开）
    }
  }
}

消费者：Consumer 函数式 Bean

java 
// payment-service / PaymentConsumer
@Configuration
public class PaymentConsumer {

  @Bean
  public Consumer<OrderCreated> orderCreatedConsumer(PaymentService svc) {
    return event -> {
      log.info("收到 OrderCreated：orderId={}", event.orderId());
      svc.initiatePayment(event);
    };
  }

  @Bean
  public Consumer<PaymentCompleted> paymentCompletedConsumer(OrderServiceClient client) {
    return event -> client.updateOrderStatus(event.orderId(), OrderStatus.PAID);
  }
}

消费者组、分区键与有序性

Kafka 的消费者组决定负载均衡：同组内每个分区只由一个消费者处理，实现并行；不同组各自独立消费全量消息。ShopFlow 关键设计：

  • orderCreated topic 分区键：orderId.hashCode() % partitions，保证同一订单事件顺序。
  • payment 消费者组：payment-service 的多个实例共享同一 group，分区内有序、跨分区并行。
  • analytics 消费者组：独立 group，不受 payment 消费速度影响。

生产者指定分区键

java 
// 发送时通过 MessageBuilder 设 key
Message<OrderCreated> msg = MessageBuilder
  .withPayload(event)
  .setHeader(KafkaHeaders.KEY, event.orderId().getBytes(StandardCharsets.UTF_8))
  .build();
kafkaTemplate.send("shopflow.order.created", msg);
  • 同一订单的 Created → Paid → Shipped 严格有序
  • 每个分区内顺序保证，跨分区不保证
  • 合适：订单状态机、库存扣减流水
  • 同一用户的所有操作有序
  • 热点用户（VIP）会导致分区倾斜
  • 适用：用户行为分析、会话回放

Redis 缓存穿透/击穿/雪崩防护

ShopFlow 商品详情是典型「读多写少」场景。引入 Redis 缓存后面临三类经典问题：

三问题对比与对策

问题现象ShopFlow 对策
缓存穿透 查不存在的数据，缓存中没有、直接穿透到 DB 布隆过滤器 + 空值短期缓存（TTL 60s）
缓存击穿 热点 key 过期瞬间，大量请求同时打到 DB 互斥锁（SETNX）只让一个线程重建缓存
缓存雪崩 大量 key 同时过期，DB 瞬时压力飙升 过期时间加随机值 ±20%；多级缓存 + 限流

缓存穿透防护：布隆 + 空值

java 
// shopflow-product-service / ProductCacheService
public Product getProduct(String sku) {
  // 1. 布隆过滤器预判（不存在则直接返回 null）
  if (!bloomFilter.mightContain(sku)) return null;

  // 2. 查缓存（含空值哨兵）
  String cacheJson = redisTemplate.opsForValue().get("product:" + sku);
  if (cacheJson != null) {
    return "NULL".equals(cacheJson) ? null : fromJson(cacheJson);
  }

  // 3. 查 DB
  Product p = productRepo.findBySku(sku);
  if (p == null) {
    redisTemplate.opsForValue().set("product:" + sku, "NULL", 60, TimeUnit.SECONDS);
  } else {
    redisTemplate.opsForValue().set("product:" + sku, toJson(p), 30, TimeUnit.MINUTES);
  }
  return p;
}

缓存击穿防护：互斥锁

java 
public Product getProductWithLock(String sku) {
  String cacheJson = redisTemplate.opsForValue().get("product:" + sku);
  if (cacheJson != null) return "NULL".equals(cacheJson) ? null : fromJson(cacheJson);

  // 互斥锁：「谁拿到锁谁重建」
  String lockKey = "lock:product:" + sku;
  boolean locked = redisTemplate.opsForValue()
      .setIfAbsent(lockKey, "1", 10, TimeUnit.SECONDS);
  if (locked) {
    try {
      Product p = productRepo.findBySku(sku);
      redisTemplate.opsForValue().set(
        "product:" + sku, p == null ? "NULL" : toJson(p),
        30 + ThreadLocalRandom.current().nextInt(0, 6), TimeUnit.MINUTES); // 随机过期防雪崩
      return p;
    } finally {
      redisTemplate.delete(lockKey);
    }
  } else {
    // 未拿到锁：短暂 sleep 后重试读缓存
    Thread.sleep(50);
    return getProductWithLock(sku);
  }
}
常见误区
  • 所有 key 设同一 TTL → 批量过期雪崩
  • 查不到也不写空哨兵 → 穿透
  • 多线程同时重建热点缓存 → 击穿 DB
防护组合
  • TTL = 基准值 + random(0, 20%)
  • 不存在也缓存 NULL 哨兵（短 TTL）
  • SETNX 互斥锁 + 逻辑过期双写

Cache-Aside 在商品读模型上的应用

Cache-Aside（旁路缓存） 是 ShopFlow 选用的缓存模式：应用直接与缓存和 DB 交互，缓存层不自动回源。读写路径清晰——

Cache-Aside 读写流程
flowchart TD
  subgraph 读路径
    R1[请求 product:SKU-1] --> R2{缓存命中?}
    R2 -->|是| R3[返回缓存值]
    R2 -->|否| R4[查 DB]
    R4 --> R5[写回缓存 + 返回]
  end
  subgraph 写路径
    W1[管理员更新商品] --> W2[更新 DB]
    W2 --> W3[删除缓存 key]
    W3 --> W4[下次读自然回源重建]
  end

写路径选择「删缓存」而非「更新缓存」，因为更新可能做无用功（紧接的后续更新会覆盖）、且删缓存天然无并发写缓存的一致性问题。

写路径：先 DB 后删缓存（双删可选）

java 
@Transactional
public void updateProduct(String sku, ProductUpdateRequest req) {
  // 1. 更新 DB
  productRepo.updateBySku(sku, req);
  // 2. 删除缓存（失败可异步重试）
  redisTemplate.delete("product:" + sku);
}

逻辑过期：防热点 key 击穿进阶

热点商品的物理 TTL 设为 永不过期，额外存储一个 logicExpireAt 字段。读时发现逻辑过期 → 获取互斥锁 → 开异步线程重建 → 当前请求仍返回旧值（容忍短时不一致）。

java 
// 缓存值包装
public record CachedProduct(Product product, long logicExpireAt) {}

public Product getWithLogicalExpire(String sku) {
  CachedProduct cp = getCached(sku);
  if (cp == null) return getProductWithLock(sku); // 首次加载

  if (System.currentTimeMillis() > cp.logicExpireAt()) {
    // 逻辑过期，异步重建
    String lockKey = "lock:product:" + sku;
    if (redisTemplate.opsForValue().setIfAbsent(lockKey, "1", 10, TimeUnit.SECONDS)) {
      executor.submit(() -> {
        Product fresh = productRepo.findBySku(sku);
        redisTemplate.opsForValue().set("product:" + sku,
          toJson(new CachedProduct(fresh, System.currentTimeMillis() + 30 * 60_000L)));
        redisTemplate.delete(lockKey);
      });
    }
  }
  return cp.product(); // 返回旧值，不阻塞
}
先想 10 秒：Cache-Aside 在高并发写时，先删缓存再写 DB 会有什么问题？

线程 A 删缓存 → 线程 B 读发现 miss → 读 DB（旧值）→ 写缓存旧值 → 线程 A 写 DB（新值）→ 缓存中是旧值。所以推荐先写 DB 再删缓存（或双删：写 DB 前删一次、写完后再延时删一次）。

本章结论

每条对应上一节 h3。

  • 领域事件：不可变、过去式命名；OrderCreated/PaymentCompleted 解耦 order→payment→analytics 链；胖瘦事件权衡按需回查。
  • Spring Cloud Stream + Kafka：StreamBridge.send() 发消息，函数式 Consumer<T> 收消息；Binder 抽象屏蔽 Kafka Client 细节。
  • 分区与有序：按 orderId 分区保证同一订单事件顺序；消费者组独立消费；手动提交 offset 防丢消息。
  • 三缓存问题：穿透→布隆+空值哨兵；击穿→互斥锁 SETNX；雪崩→TTL 随机化 20% + 多级缓存。
  • Cache-Aside：读命中直接返回、miss 回 DB 并回填；写先 DB 后删缓存，热点 key 用逻辑过期 + 异步重建容忍短时不一致。

动手练习

在 order / payment 间加入 Kafka 事件流，为商品详情加 Redis 缓存并模拟三类缓存问题。

操作步骤

  1. 启动 Kafka (Docker) 并配置 spring.cloud.stream.kafka.binder.brokers；order 发布 OrderCreated，消费侧日志确认收到。
  2. 对照「消费者组」说明：起两个 payment 实例（同 group），验证同一分区内只有一个实例消费。
  3. 为商品详情实现 Cache-Aside：GET /products/{sku} 先查 Redis、miss 回 DB；观察首次慢、二次快。
  4. 模拟击穿：在 Redis 中删除热点 key 后立即 10 并发压测，确认仅 1 条 SQL 打到 DB（互斥锁生效）。

判断练习

  1. Kafka 消费者若用 enable.auto.commit=true（默认），处理消息中途进程崩溃。消息会丢还是重复？如何修正？

    参考答案

    会丢：自动提交在 poll 后即提交 offset，业务未处理完也会被标记为已消费。修正：设为 false，业务处理完成后手动 acknowledgment.acknowledge()。但手动提交后若崩溃则消息重复，需消费者幂等。

  2. 所有商品缓存 key 的 TTL 均设为 30min，无随机偏移。缓存预热后 30 分钟时 DB CPU 飙至 95%。判断问题类型并给出两处修改。

    参考答案

    缓存雪崩：统一过期导致同时回源。修改：① TTL = 30min + Random(0, 6) 分钟随机偏移；② 对热点 SKU 采用逻辑过期 + 异步重建，物理永不过期。
